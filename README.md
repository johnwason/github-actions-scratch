# Robot Raconteur Go bindings

Go bindings for [Robot Raconteur](https://github.com/robotraconteur/robotraconteur).
They are built the way the C# and Java bindings are: SWIG wraps the C++ core
(using the upstream shared `SWIG/*.i` files), and a hand-written Go runtime
on top of it provides an idiomatic API. `RobotRaconteurGenGo` generates Go
packages from `.robdef` files. It is a sibling of `RobotRaconteurGen`,
written to be merged into it as `--lang=go`.

Status: Linux (x86_64) only. The native core is linked statically into Go
programs through cgo.

## Layout

| Path | Contents |
|------|----------|
| `robotraconteur/` | runtime package (`import rr "github.com/robotraconteur/robotraconteur_go/robotraconteur"`) |
| `robotraconteur/internal/swig/` | raw SWIG proxies and cgo flags (generated by the build) |
| `swig/` | Go SWIG interface: `RobotRaconteurGo.i`, `shared_ptr`/`intrusive_ptr` support, typemaps, error plumbing, `postprocess_go.py` |
| `gen/` | `RobotRaconteurGenGo` (`GoServiceLangGen.cpp`, CLI in `main.cpp`) |
| `test/` | golden generator output, Go ports of the upstream test services and clients, loopback/interop/crosscheck tests |
| `examples/reynard_the_robot/` | Reynard client, simulated service, `go:generate` usage |
| `docker/`, `scripts/` | podman dev image and build/test scripts |
| `.github/workflows/ci.yml` | Linux CI |

## Building

Everything builds inside the podman dev image (Ubuntu 24.04, SWIG 4.2,
Go 1.27). The `robotraconteur` checkout is expected next to this directory
and is mounted read-only. It must be upstream `7cd1610c` with the patches in
[gen/upstream_merge/core-patches](gen/upstream_merge/core-patches) applied
(`git am`). The patches fix a connector deadlock and add the SWIG
declarations the bindings use; see
[gen/upstream_merge/README.md](gen/upstream_merge/README.md).

```sh
scripts/podman.sh image          # build the dev image (once)
scripts/podman.sh build          # core, SWIG module, native lib, generator
RR_TESTING=ON JOBS=1 scripts/podman.sh build   # also the upstream C++ test programs (for interop tests)
scripts/podman.sh test           # golden test, go vet, go test ./... (no network)
scripts/podman.sh shell 'go test ./examples/...'
```

Build stages:

- Upstream core goes into `build/rr` and is installed to `build/install`.
- The SWIG module, `libRobotRaconteurGoNative.a` and `RobotRaconteurGenGo` go into `build/go`.
- The SWIG Go file and `cgo_flags_linux.go` are written to `robotraconteur/internal/swig/`.

Go programs then build with a plain `go build`, and SWIG is not needed at that point.

## Generating service packages

```sh
RobotRaconteurGenGo --thunksource --output-dir gen \
    --go-import-prefix=example.com/myrobot/gen \
    -I robdef experimental.reynard_the_robot.robdef
```

Each service definition becomes one package, with dots replaced by `__`: for
example `gen/experimental__reynard_the_robot`. `--go-import-prefix` is the
import path of the output directory, used when one service imports another.
`--go-runtime-import` overrides the runtime import path. The usual way to run
it is through `go:generate`; see
[examples/reynard_the_robot/generate.go](examples/reynard_the_robot/generate.go).

Generated code:

| robdef | Go |
|--------|----|
| `struct` | `*Name` (nil is null) |
| `pod`, `namedarray` | value structs; fixed arrays are Go arrays |
| `enum` | typed `int32` constants |
| `exception` | `*Name` error type wrapping `*rr.Error` (use `errors.As`) |
| `object` | interface `Name`, client stub, skel, `NameDefaultImpl` |
| `double[]`, `int32[*]`, `string{int32}`, `varvalue` | `[]float64`, `*rr.MultiDimArray[int32]`, `map[int32]string`, `any` |
| `property x` | `Get_x(ctx) (T, error)`, `Set_x(ctx, v) error` |
| `function f` | `F(ctx, args...) (ret, error)` |
| `objref o` | `Get_o(ctx[, index]) (Obj, error)` |
| `event e`, `callback c` | `Get_e() *rr.Event[func(...)]`, `Get_c() *rr.Callback[func(...) (..., error)]` |
| `pipe`, `wire`, `memory` | `Get_x()` returning `*rr.Pipe[T]`, `*rr.Wire[T]`, `rr.ArrayMemory[T]` / `MultiDimArrayMemory[T]` / pod memories |
| generator functions | `rr.Generator1[R,P]`, `Generator2[R]`, `Generator3[P]` (`Next(ctx, ...)`) |

Member names follow the C++ thunks: accessors are `get_`/`set_` plus the
member name unchanged (`Get_`/`Set_` so Go exports them), and functions
keep their name with the first letter upper case (`drive_robot` becomes
`Drive_robot`). Robot Raconteur reserves member names starting with `get_`,
`set_`, `async_` and `rr` (ignoring case), so these can't collide with each
other. Nor can they collide with the generated and runtime helpers, which
all start with `RR` (for example `RRBroadcaster_state` in a `DefaultImpl`).
The generated parameter for the context is `rr_ctx`.

## Concurrency model

There is no separate asynchronous API. Every call that goes over the
network is a synchronous Go call taking a `context.Context`. Internally it
is the core's asynchronous operation awaited by the calling goroutine: the
goroutine parks on a channel, so no OS thread is held while a request is in
flight. Use goroutines for concurrency.

- **Timeouts.** A ctx deadline bounds each request, together with the node
  request timeout (`Node.SetRequestTimeout`).
- **Cancellation.** Cancelling ctx returns `ctx.Err()` immediately. The core
  can't cancel a request, so it finishes in the background. A late result
  that holds a resource, such as a connection or a pipe endpoint, is released.
- **Waits.** The `*Wait` methods (`ReceivePacketWait`, `WaitInValueValid`,
  `DefaultClientWait`) also wait on the goroutine.
- **Close.** `Close()` methods and `DisconnectService` take no ctx; they are
  bounded by the request timeout.
- **Service members run on their own goroutine.** The core's request
  thread is released at once, so implementations can block and make calls.
  `rr_ctx` describes the request (`rr.CurrentEndpoint`,
  `rr.CurrentServicePath`, `rr.CurrentServerContext`,
  `rr.CurrentAuthenticatedUser`). Objref lookups (`Get_o` on a service)
  still run on the request thread.
- **Inline callbacks.** Events, callbacks, wire and pipe notifications and
  timers run on core threads. They should return quickly; requests made
  from them hold that thread until they complete.
- **Thread-pinning exceptions.** Memories and monitor locks
  (`WithMonitorLock`) still hold an OS thread for their duration.

## Client

```go
setup, err := rr.ClientNodeSetup(rr.WithServiceTypes(reynard.Factory))
if err != nil { ... }
defer setup.Close()

ctx := context.Background() // or a context with a deadline / cancellation
obj, err := setup.Node.ConnectService(ctx, "rr+tcp://localhost:29200?service=reynard")
if err != nil { ... }
defer setup.Node.DisconnectService(obj)
c := obj.(reynard.Reynard)

c.Get_new_message().Connect(func(msg string) { fmt.Println(msg) })
if err := c.Teleport(ctx, 0.1, -0.2); err != nil { ... }
state, ts, err := c.Get_state().PeekInValue(ctx)
```

Wires, pipes, memories, object locks (`Node.RequestObjectLock`, `WithMonitorLock`),
subscriptions (`Node.SubscribeService`, `SubscribeServiceByType`,
`SubscribeServiceInfo2`, and wire/pipe subscriptions) and local-transport
discovery are supported.

## Service

Embed the generated `DefaultImpl` and override what you implement. Then
register the object:

```go
type robot struct{ reynard.ReynardDefaultImpl }

func (r *robot) Teleport(ctx context.Context, x, y float64) error { ... }

setup, err := rr.ServerNodeSetup("experimental.reynard_the_robot", 29200,
    rr.WithServiceTypes(reynard.Factory))
ctx, err := setup.Node.RegisterService("reynard", "experimental.reynard_the_robot.Reynard", &robot{})
```

Other service-side features:

- **Readonly wires and pipes.** These get broadcasters in the `DefaultImpl` (`RRBroadcaster_state`). `rr.NewBroadcastDownsampler` adds per-client downsampling.
- **Security.** Pass `rr.WithSecurityPolicy(&rr.ServiceSecurityPolicy{Authenticator: rr.NewPasswordFileUserAuthenticator(data), Policies: ...})` to `RegisterService`. Authenticators can also be Go functions (`rr.UserAuthenticatorFunc`) that return an `*rr.AuthenticatedUser` or an error. Service members can call `rr.CurrentAuthenticatedUser(ctx)` and `rr.CurrentServerContext(ctx)`.

## Errors

Failures are returned as Go `error` values. Network, transport, remote and
framework errors never panic.

- Built-in errors are `*rr.Error{Code, Name, Message, SubName, Param}`, with
  sentinels for `errors.Is`: `rr.ErrConnectionError`, `rr.ErrTimeout`,
  `rr.ErrInvalidArgument`, and so on.
- Constructors for service implementations: `rr.NewInvalidArgument("...")`, and the others.
- Service-defined exceptions are generated types, matched with `errors.As`.
- A service member returning an `error` sends it to the client. A panic in a
  service member, or in any other callback that C++ invokes, is recovered and
  becomes `RobotRaconteur.UnknownError`.
- Panics are kept for programmer errors, such as a nil receiver.

## Logging

```go
node.SetLogLevel(rr.LogLevelDebug)            // or SetLogLevelFromString / SetLogLevelFromEnv
node.SetLogRecordHandler(func(r rr.LogRecord) { log.Println(r) })
node.OpenLogFile("rr.log", true)
```

## Timers

`Node.CreateTimer(period, oneshot, func(rr.TimerEvent, error))` and
`Node.CreateRate(hz)` follow the node's time base, unlike `time.Ticker`.
They matter when a custom time provider is installed (simulation).

## Testing

`scripts/podman.sh test` runs in a container with `--network=none`. Only
loopback TCP, local and intra transports are used, and network discovery is
not enabled. The tests cover:

- `test_gen_go`: `RobotRaconteurGenGo` output for TestService1-3 is compared with `test/golden/` (update it with `scripts/update_golden.sh`).
- `test/loopback`: Go service with a Go client in one process.
- `test/interop`: the Go ports of `ServiceTestClient` and `ServiceTestClient2`, plus subscription tests, against the upstream C++ `robotraconteur_test_server`.
- `test/crosscheck`: the upstream C++ client test programs, plus the Go clients, against the Go ports of the test services.
- `examples/reynard_the_robot/client`: the example client against the simulated service.

The interop and crosscheck tests need `RR_TESTING=ON` builds. Without the C++
test programs they skip.

## Not yet supported

- Windows and macOS. The runtime is OS-neutral, but the core and toolchain setup for cgo is Linux-only for now.
