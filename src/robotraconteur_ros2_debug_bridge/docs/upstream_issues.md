# Upstream issues found by this repo's tests

Defects in dependencies (Robot Raconteur, ROS 2) that the tests hit, with the
workaround in place. Suppressions are narrow (a function or class, never a
library this repo is part of) and each has an entry here.

| Where | What | Workaround | Status |
|---|---|---|---|
| Robot Raconteur master `7cd1610c`, client connect path | ThreadSanitizer lock-order inversion (potential deadlock): `RobotRaconteurNode_connector::connected_transport` holds the connector mutex and calls `ClientContext::AsyncConnectService` (ClientContext mutex); `ClientContext::AsyncConnectService7` holds the ClientContext mutex and its completion `RobotRaconteurNode_connector::connected_client` takes the connector mutex. Both on RR thread-pool threads during `ConnectService` over LocalTransport. Seen in `test_component_lifecycle` (the tests' client node) on the GitHub TSan job, 2026-11-14. | `deadlock:RobotRaconteur::detail::RobotRaconteurNode_connector` in `scripts/in-container/tsan.supp` | Reported to the RR maintainer (the user), 2026-11-14 |
| rcl (Jazzy) | One rosout publisher per ROS node name, process-wide: creating a second node with the same fully qualified name orphans the new node's publisher (LeakSanitizer). | Tests give nodes that are expected to fail distinct namespaces. | Known upstream behavior |
| Robot Raconteur master `7cd1610c`, `ConstantDefinition_CheckScalar` (`ServiceDefinition.cpp`) | `int8`/`uint8` constants: the value is checked with `lexical_cast` into `int8_t`/`uint8_t`, which are char types, so only a value that is one character verifies. `constant int8 A 2` parses, but `constant int8 A -2` and `constant uint8 A 200` fail with "Invalid constant definition". Found by the B2 generator (`sensor_msgs/NavSatStatus`), 2026-11-14. | The generated definitions widen 8-bit (and bool) constants to `int16`/`uint16` (`src/type_mapper.cpp`). | Reported to the RR maintainer (the user), 2026-11-14 |
| Robot Raconteur master `7cd1610c`, wires: `WireServerBase::WireCommand` / `WireClientBase` | A value set on a server wire connection from the connect callback is lost. The server calls the connect callback, where `WireBroadcasterBase::ConnectionConnectedBase` sets the current out value, before the connect response is sent. The client creates its connection only on that response, and `WireClientBase::WirePacketReceived` drops packets without a connection. So a late wire connection does not get the current value until the next change; for a latched (transient-local) topic, there is no next change. Found by `test_topics` (late wire connection), 2026-11-15. | The bridge's `WireFanout` sends the current value again 50 ms and 1 s after a connection (`src/generic_service.cpp`). | Reported to the RR maintainer (the user), 2026-11-15 |
| rcl (Jazzy), per-node type description cache (`rcutils_hash_map` in the node) | Creating and destroying publishers/subscriptions on one node from different threads at the same time races on the cache (ThreadSanitizer: `rcutils_hash_map_get` on a Robot Raconteur thread creating a generic publisher, against `rcutils_hash_map_set` on the executor thread). An executor thread destroys a subscription when it drops the last reference after a callback. Found by the B4 TSan run 43666640655, 2026-11-15. | The proxies' entities live on a node of their own that one bridge thread creates, spins and destroys (`src/proxy_executor.*`, docs/topics.md). A second TSan run (43668608568) showed that one thread for our own entity operations is not enough on a shared node: the host's executor reads the cache too (most likely the node's `~/get_type_description` service). | Known upstream behavior (rcl is not thread-safe per node); not reported |
| Robot Raconteur master `7cd1610c`, `ServerContext::AsyncProcessCallbackRequest` (`Service.cpp`) | Every asynchronous callback request completes at once with neither a result nor an error, and the client's real answer is then dropped. The send-completion handler is `AsyncProcessCallbackRequest_err`. Robot Raconteur calls it with a null error when the send succeeds, and it does not check for that: it erases the outstanding request and invokes the handler with a null exception. Its debug log line also dereferences the null error. Found by `test_services` (a client serving a ROS service), 2026-11-15. | Served requests call the blocking `ProcessCallbackRequest` on a worker thread per served service (`src/service_proxy.cpp`), as generated code does. | Reported to the RR maintainer (the user), 2026-11-15 |
| Fast DDS 2.14 (`rmw_fastrtps_cpp`, Jazzy), shared-memory transport | ThreadSanitizer data race: the `dds.shm.*` thread writes a `TopicPayloadPool` payload buffer (`TopicPayloadPool::get_payload`) while a reader thread deserializes the same buffer (fastcdr `Cdr::deserialize_array`). Both stacks are entirely in Fast DDS/fastcdr. Seen in `test_topics__rmw_fastrtps_cpp` on the GitHub TSan job (run 43682189102), 2026-11-15. | `race:eprosima::fastrtps::rtps::TopicPayloadPool::` in `scripts/in-container/tsan.supp` (also seen through `do_get_payload`, run 43683767686) | Upstream (Fast DDS); not reported |
| Robot Raconteur master, `RobotRaconteurCore` CMake target, with conda-forge Boost on Windows | The target exports `_WIN32_WINNT=0x0600` (Windows Vista) as a public compile definition. With it, Boost.Winapi does not declare `WaitOnAddress` (Windows 8), but Boost.Atomic's `wait_ops_windows.hpp` still names it in a template. Under MSVC's two-phase name lookup (`/permissive-`), every file that includes Robot Raconteur headers fails to compile (`C2039: 'WaitOnAddress': is not a member of 'boost::winapi'`). Robot Raconteur itself builds because it does not use `/permissive-`. Found by the bridge's first Windows CI run (43682189102), 2026-11-15. | MSVC flags `/permissive- /Zc:twoPhase-` (`CMakeLists.txt`): standard conformance kept, two-phase lookup off. | To report to the RR maintainer (the user) |
| rclcpp (Jazzy), `MultiThreadedExecutor` entity recollect | ThreadSanitizer data race: while a component loaded by `rclcpp_components::ComponentManager` is added, one executor worker frees an object that another used under a mutex in `NodeBase::callback_group_in_node`. The ordering is a `shared_ptr` refcount inside the uninstrumented librclcpp. Both stacks are entirely in librclcpp. Seen in `test_components` on the GitHub TSan job (run 43683767686), 2026-11-15; `rmw_intraprocess` has the same entry (`test_composition_demo`). | `race:rclcpp::node_interfaces::NodeBase::callback_group_in_node` in `scripts/in-container/tsan.supp` | Known upstream (same as `rmw_intraprocess`) |
| Robot Raconteur master, client `ClientContext::AsyncFindObjRef1` (`Client.cpp`) | Dangling `boost::string_ref`: `objectdef = SplitQualifiedName(objecttype).get<0>()` views `objecttype`, and the same call `AsyncPullServiceDefinitionAndImports(objectdef, boost::bind(..., RR_MOVE(objecttype), objectdef.to_string(), ...))` moves `objecttype` away. The client then asks the server for a definition named by whatever the memory holds. The bridge's debug log shows requests for `"ros2_debug_bridge.subscribers[2]"` and `"ros2_debug_bridge.subscri"` (`Unknown service type`), and the client's `FindObjRef` fails with `ServiceNotFound`. Undefined behavior; it shows with the MSVC build (Windows CI runs 43687123934, 43688857823, 2026-11-15: random topic, served-service and CLI tests) and not with GCC. It happens whenever a client must pull an objref's type at `FindObjRef`, which every type the bridge registers at run time needs. Fix: keep `objectdef` as a `std::string` (or move `objecttype` only after the last use of the view). | None in the bridge: it needs the Robot Raconteur fix. The Windows CI job applies `ci/patches/robotraconteur-asyncfindobjref1-dangling-string_ref.patch` to its Robot Raconteur clone until master has a fix (user decision, 2026-11-15). | To report to the RR maintainer (the user) |
