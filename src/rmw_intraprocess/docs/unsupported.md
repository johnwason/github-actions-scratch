## Upstream defects seen in M7 conformance (not excluded, pending user review)

These failures occur with the reference `rmw_fastrtps_cpp` too (same container,
same selection, `CONFORMANCE_RMW=rmw_fastrtps_cpp scripts/conformance.sh ...`),
so they are defects of the upstream code or tests, not of this RMW. Nothing is
filtered for them; they are recorded here so the M7 results can be read.

| Where | What | Evidence |
|---|---|---|
| rclcpp `test_wait_set` (release) | Intermittent SIGSEGV at process exit after all cases pass: rclcpp's default `Context` is destroyed after a static `std::unordered_set` in `rclcpp/src/rclcpp/context.cpp` (static destruction order; ASan reports heap-use-after-free at `context.cpp:375`). | 30 runs each: 2 crashes with this RMW, 5 with `rmw_fastrtps_cpp`. |
| rcl, built with ASan/UBSan (28 test targets) | UBSan misaligned load in `rcl/src/rcl/node_type_cache.c:38` (aborts with `-fno-sanitize-recover`), UBSan in `test_logging.cpp:240`, and leaks in the tests. | The same 28 targets fail with `rmw_fastrtps_cpp` (891 cases, 24 errors, 28 failures in both runs). |
| rclcpp, built with ASan/UBSan (15 test targets) | new/delete type mismatch in `test_allocator_common`, UBSan in `rclcpp/src/rclcpp/qos.cpp:65` and `allocator_memory_strategy.hpp:240`, the exit-order use-after-free above, and leaks owned by upstream objects (fault-injection `*_fini_errors` tests, graph listener, executors). Every leak report involving this RMW's code is an indirect leak under an upstream-owned allocation. | The same 15 targets fail with `rmw_fastrtps_cpp` (it also fails `test_publisher` and `test_subscription`). |
| rclcpp `test_executors_busy_waiting` `EventsExecutor.test_spin` (ASan) | Timing race in the test (condition variable waits without a predicate can miss the notification and wait the full 10 s). | 20 repeats, twice per RMW: 2 failures in 40 runs with each RMW. |
| system_tests `test_rclcpp` `gtest_waitable`; `test_communication` `test_messages_c` (ASan) | Fail under ASan with both RMWs. | Same result with `rmw_fastrtps_cpp`. |

## Upstream defects and limits found by the torture tests (M8c, pending user review)

Found by `rmw_intraprocess_torture` (2026-11-14). None involves this RMW's
code; the torture components avoid each trigger so the rest of the matrix
runs, and each workaround is commented where it is applied.

| Where | What | Workaround in the torture mix |
|---|---|---|
| rclcpp `IntraProcessManager` (intra-process comms on) | `add_subscription` holds the IPM mutex while promoting a weak publisher pointer; if another thread has just dropped that publisher, the IPM's temporary is the last reference, `~PublisherBase` calls `remove_publisher`, which locks the same (non-recursive) mutex: `std::system_error` "Resource deadlock avoided", then terminate. RMW-independent (pure rclcpp stack). Variant with the IPM's reader-writer lock: an executor thread in `matches_any_publishers` (taking a message, IPM lock held) promotes a publisher that another thread just dropped, `~PublisherBase` calls `remove_publisher`, which waits for the write lock this thread holds: a self-deadlock (hang), seen when a lifecycle node's `on_cleanup` destroyed its lifecycle publisher under a MultiThreadedExecutor (about 1 in 150 shutdown runs). Any application destroying publishers with intra-process comms on (e.g. lifecycle nodes) can hit it. | `EntityChurn` and `LifecycleChurn` are loaded without intra-process comms (`test/test_torture.cpp`). |
| rcl per-node type description cache (`rcl_node_type_cache_register_type` / `unregister_type`, called by every `rcl_*_init` / `rcl_*_fini`) | No lock. Creating and destroying entities of one node from several threads (including executor threads that drop the last reference) corrupts the cache: "Failed to unregister type, hash not present in map", then `rosidl_runtime_c__String__fini` calls `exit()`. rcl documents entity init/fini as not thread-safe; rclcpp adds no lock. | Each churn thread (`EntityChurn`, `ServiceStorm` churn) creates and destroys entities only on private nodes that no other thread or executor touches. Also reached through `rclcpp::shutdown()` while threads create/destroy nodes (rcl's process-wide rosout logger map; TSan, CI): `ShutdownDuringMix` stops `EntityChurn` before shutting down. Also reached through `ComponentManager`'s `unload_node` under a MultiThreadedExecutor (an executor thread drops the last reference to one entity while the component destructor finalizes the others; TSan, CI): the driver stops the executor before destroying the components. |
| rclcpp `StaticSingleThreadedExecutor` (Jazzy) | `spin()` executes one ready executable per wait, always in the same order (subscriptions first). Under saturating load the later entities starve; with closed-loop load (clients sending back to back) the service that would stop the load is never reached (livelock). `SingleThreadedExecutor` executes the whole wait result and does not starve. | The short mix bounds every workload (message and request counts), so it drains under every executor. Unbounded soak runs should use the other executors. |
| rclcpp_action server during `rclcpp::shutdown()` | Executor callbacks still run after the context is shut down; rcl then refuses the action server's publishers ("feedback/status publisher is invalid": rcl checks the context), and `rclcpp_action::ServerBase::execute_goal_request_received` (and `publish_feedback`) throw `RCLError`, which propagates out of `spin()`. A spin thread that does not catch it (as in `component_container`) terminates the process at shutdown; on a MultiThreadedExecutor the exception is thrown on one of the executor's own worker threads, where nothing can catch it, so the process always aborts (seen under ASan, about 1 run in 8). RMW-independent (the refusal is in rcl). | The driver's spin thread catches exceptions (allowed after shutdown, a failure while rclcpp runs). `ShutdownDuringMix` first stops the action storms and waits until every goal request reached the server and finished, then shuts down with everything else still busy. |
| rclcpp_action result request before goal acceptance | `ServerBase::execute_goal_request_received` sends the goal response (`server.cpp:536`, rclcpp 28.1.22) before it registers the goal in rcl (`rcl_action_accept_new_goal`, `:576`). The client asks for the result as soon as the goal is accepted; under a MultiThreadedExecutor that request can be handled in between, and the server answers `STATUS_UNKNOWN` (`:724-728`), so the client sees `ResultCode::UNKNOWN` although the goal then runs and succeeds. RMW-independent; a fast in-process RMW makes it likelier. Seen once in CI (Linux, RoboStack). | `ActionStorm` counts such results as `result_unknown` (not an error); the server must still finish every accepted goal, and ABORTED stays an error. |
| `rmw_fastrtps_cpp` as a torture reference | In the same mix it loses RELIABLE samples (e.g. 1596 of 1800), times out service requests and finally hangs, under several executors. It cannot serve as a reference here. | The torture driver runs against this RMW only (CMakeLists comment says how to repeat the comparison). |

Not a defect: with the default `ServicesQoS()` (KEEP_LAST 10) a busy server
drops the oldest queued requests, as on any RMW; `ServiceStorm` uses deeper
service queues so requests in flight are never dropped by design. The same
holds for actions: rcl_action's goal/cancel/result services default to
KEEP_LAST 10, and under the StaticSingleThreaded executor (waitables served
last) a busy action server dropped the oldest goal requests; `ActionStorm`
uses deeper queues.
